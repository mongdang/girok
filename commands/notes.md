# /notes

평상시에는 훅이 전부 처리하므로 이 명령을 칠 일이 없다. **어긋났을 때 부르는 리셋
버튼**이다. 서브명령은 없다 - 저장소 상태를 보고 필요한 동작을 판단한다.

## 절차

### 0. Python 부터 확인한다

아래 절차는 전부 Python 스크립트이고, 훅도 Python 으로 돈다. 없으면 `/notes` 도 훅도
동작하지 않으므로 다른 것보다 먼저 본다.

```
python --version
```

| 결과 | 다음 |
|---|---|
| 3.10 이상 | §1 |
| 명령이 없거나 3.10 미만, Windows 에서 `py -3 --version` 은 3.10 이상 | 이하 명령의 `python` 을 `py -3` 으로 바꿔 실행한다. 훅 래퍼도 같은 순서로 찾으므로 설치는 필요 없다 |
| 쓸 수 있는 Python 이 없다 | 아래 설치 |

Windows 의 `python3` 가 아무 출력 없이 끝나는 것은 Microsoft Store 바로가기다 - Python 이
아니다. `uv python list` 에만 보이는 Python 도 PATH 에 없어 훅이 쓰지 못하니, 있다고 치지
않는다.

**설치는 승인을 받고 한다.** `AskUserQuestion` 으로 "이 PC 에 Python 3.10+ 가 없습니다 -
지금 설치할까요?" 를 묻고, 어떤 명령을 돌릴지 그대로 보여준다. 직접 설치하겠다고 하면
[python.org](https://www.python.org/downloads/) 를 안내하고("Add python.exe to PATH" 체크)
여기서 멈춘다.

| OS | 명령 |
|---|---|
| Windows | `winget install -e --id Python.Python.3.13 --scope user --accept-package-agreements --accept-source-agreements` |
| macOS | `brew install python@3.13` |
| Linux | 배포판 패키지 관리자(`apt install python3` 등). `sudo` 가 필요하면 실행하지 말고 명령을 사용자에게 안내한다 |

`winget`·`brew` 가 없으면 설치 도구부터 깔지 않는다 - python.org 를 안내하고 멈춘다.

설치 뒤에 확인할 것 둘:

1. **설치됐는가.** 이 세션의 PATH 는 설치 전 그대로라 `python` 은 여전히 안 잡힌다.
   설치된 실행 파일을 전체 경로로 불러 확인하고(Windows 사용자 범위 설치는
   `%LOCALAPPDATA%\Programs\Python\Python313\python.exe`), 이 `/notes` 의 나머지 명령도
   그 경로로 이어서 실행한다.
2. **PATH 에 올라갔는가.** Windows 는 사용자 PATH(`[Environment]::GetEnvironmentVariable('Path','User')`)
   에 그 폴더가 들어갔는지 본다. 없으면 훅이 다음 세션에서도 찾지 못한다 - 사용자에게
   알리고, 승인을 받아 사용자 PATH 에 추가한다.

> [!IMPORTANT]
> 끝나면 **Claude Code 를 껐다 켜라고** 알린다. 훅은 세션이 물려받은 PATH 에서 Python 을
> 찾으므로, 설치한 세션에서는 `/notes` 가 끝까지 돌아도 훅은 돌지 않는다.

### 2. 초기화 - 스냅샷이 없을 때

**먼저 백업한다.** 이 저장소에 아무것도 쓰기 전에 원본을 통째로 남긴다. `git init` 도,
뼈대 생성도 이 뒤다 - 순서가 바뀌면 백업이 담는 것은 girok 이 이미 손댄 상태다.

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/notes_adopt.py" backup
```

워크스페이스(저장소를 여러 개 담은 상위 폴더)로 보이면 여기서 멈춘다. 그때는 작업할
저장소 폴더로 옮겨 다시 켤 것.

**그리고 저장소를 읽는다.** 기본값으로 뼈대를 뿌리기 전에, 이 저장소가 이미 어떤 관례를
쓰고 있는지 조사한다 - 안 하면 진짜 문서 옆에 빈 문서 한 벌이 더 생긴다.

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/notes_survey.py"
```

읽기 전용이다. 출력은 **제안**이며, 그대로 쓰지 않는다:

- 제안된 설정(진행기록 위치·현황판·결정 기록·모듈)을 사용자에게 **그대로 보여주고**
  틀린 것이 있는지 묻는다. 특히 "현황판 후보가 여럿" 같은 항목은 사람만 답할 수 있다.
- "살펴볼 것" 은 초기화와 별개 문제다. 지금 고칠지, 적어두고 넘어갈지 물어본다 -
  임의로 고치지 않는다.
- 조사가 현황판을 못 찾았으면 새로 만들 것인지 확인한다.

`--json` 을 붙이면 제안을 그대로 `notes_init.py` 인자로 옮길 수 있다.

> [!CAUTION]
> **그리고 이 저장소가 쓸 수 있는 저장소인지 확인한다.** 참고 저장소·읽기 전용으로 합의된
> 저장소일 수 있고, 그건 저장소 안에 적혀 있지 않다. 사용자에게 저장소 경로를 그대로
> 보여주고 **"여기에 만들어도 됩니까?" 를 묻는다.** 아니라면 여기서 멈춘다.

**사용자 승인을 먼저 받는다.** 무엇을 만들 것인지 먼저 보여준다:
진행기록 폴더 이름, 안전 게이트 모듈 사용 여부, 병행 작업 모드 여부.

기본값을 제안하되, 저장소를 보고 판단한다 - 하드웨어·모션 제어 코드가 있으면 안전
게이트를 켜는 쪽을 제안하고, 그 근거를 말한다. `AskUserQuestion` 으로 한 번에 묻는다.

**병행 작업자가 있는지는 추론으로 넘어가지 않고 반드시 묻는다.** 조사는 `docs_<id>/`
폴더가 있는지만 보는데, 그건 지금까지의 모습이지 앞으로의 계획이 아니다. 틀리면 양쪽 다
비싸다 - 혼자 쓰는 저장소에 병행을 켜면 쓰기가 막히고, 둘이 쓰는 저장소에 끄면 반입
스캔이 돌지 않아 상대의 새 작업을 아무도 알려주지 않는다.

"이 저장소에서 다른 사람과 함께 작업합니까?" - 조사가 찾은 `docs_<id>/` 폴더와 커밋
이메일이 있으면 근거로 같이 보여준다.

| 답 | 다음 |
|---|---|
| 혼자 | `--no-parallel` |
| 함께 | 아래를 이어서 묻고 `--worker <본인 id>` 로 초기화한다 |

함께 작업한다면:

- **본인 id.** `git config user.email` 값을 보여주고 "이 이메일로 커밋하는 `<id>` 가
  맞습니까?" 를 확인한다. 비어 있으면 먼저 설정하게 한다 - 작업자는 이 값으로 판별된다.
- **상대 작업자의 id 와 git 이메일.** 초기화 뒤 `.claude/girok.json` 의 `workers` 에 직접
  추가한다. 이메일을 모르면 비워 둔다 - 상대가 첫 세션에서 질문을 받고 채운다.
- **master 병합·push 를 맡을 사람**(`mergeOwner`). 초기화는 본인으로 적으니, 다른 사람이면
  고친다.
- **원격 이름.** `git remote` 가 `origin` 이 아니면 `--remote <이름>` 을 넘긴다. 원격이
  아직 없으면 그 사실을 알린다 - 반입 스캔은 원격이 생긴 뒤부터 돈다.
- **작업자 브랜치.** 초기화 스크립트는 브랜치를 만들지 않는다. 초기화가 끝나면 커밋하기
  전에 본인 id 이름의 브랜치로 옮긴다 - 있으면 `git switch <id>`, 없으면
  `git switch -c <id>` 후 `git push -u <원격> <id>`. 초기화 결과를 `main`·`master` 에
  넣는 것은 병합 담당이 하는 병합이다. 상대 작업자의 브랜치는 만들어 주지 않는다 -
  상대의 첫 세션이 `[브랜치]` 줄로 안내한다.

승인 후:

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/notes_init.py" --confirm <저장소 폴더 이름> --notes-dir <이름> --repo-name <저장소명> [--remote <이름>] [--no-safety-gate] [--no-parallel] [--worker <id>]
```

`--confirm` 은 안전장치다 - 저장소 폴더 이름과 다르면 아무것도 만들지 않는다. 엉뚱한
폴더에서 실행되는 사고를 막기 위한 것이니 값을 추측해 채우지 말고, 위에서 확인받은
저장소의 이름을 쓴다.

이미 설정 파일(`.claude/girok.json`)이 있으면 그 레이아웃을 따르고, 없는 파일만
추가한다. **있던 파일은 건드리지 않는다.** 만들어진 것을 요약해 보고한다.

> [!IMPORTANT]
> 초기화 직후 사용자에게 알려야 하는 것 하나: `.claude/settings.json` 이 커밋되어야
> 팀원이 명령 없이 플러그인을 받는다. 다만 **각자 폴더 신뢰를 승인하기 전까지는
> 플러그인이 조용히 오지 않는다** - 그래서 `CLAUDE.md` 상단 게이트 블록이 필요하다.

### 2-1. 이식 - 기존 기록을 girok 자리로

뼈대만 만들고 끝내면 진짜 문서 옆에 빈 문서 한 벌이 남는다. 기존 기록을 옮긴다.

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/notes_adopt.py" plan
```

읽기 전용이다. `.claude/girok-adopt.json` 에 전수 목록과 `role` 초안이 생긴다.
백업 폴더는 저장소 바로 바깥에 `<저장소명>-girok-backup-<YYYYMMDD>` 이름으로 생긴다.

**`role` 이 `?` 인 항목은 규칙이 판단하지 못한 것이다. 그 문서를 직접 읽고 채운다.**
`apply` 는 `role` 로 거부하므로 `role` 을 채운다 - `to` 만 고치면 계속 막힌다.

| 채울 것 | 규칙 |
|---|---|
| `role` | `board`·`adr`·`doc` 중 하나. 옮기지 않기로 했으면 `keep` |
| `to` | 옮길 자리. **손으로 적는다** |
| `merge` | 다른 문서에 합칠 때만. **`merge` 를 적으면 `to` 는 `null` 로 둔다** |

> [!WARNING]
> **`plan` 을 다시 돌리면 채운 것이 사라진다.** `plan` 은 매핑을 읽지 않고 저장소만
> 보고 목록을 통째로 다시 만든다 - 해소한 `role`, 손으로 쓴 `merge`, `keep` 이 전부
> 날아간다. 그래서 손으로 채운 값이 있으면 `plan` 은 덮어쓰지 않고 거부한다. 표만
> 다시 보려면 `plan --dry-run`, 정말 처음부터 다시 하려면 `plan --reset-mapping` 이다.

`merge` 의 값은 **이동 후 경로**로 적는다. 병합은 이동이 끝난 뒤에 일어나므로, 표에서
읽은 현재 이름(`STATE.md`)을 적으면 그 문서는 이미 `PROGRESS.md` 로 가 있다 - 대상이
없으면 `apply` 가 거부한다.

채운 결과를 표로 사용자에게 보여주고 승인을 받는다. `?` 가 하나라도 남으면 다음 단계가
거부한다 - 그리고 매핑 파일 자체가 없으면 `apply` 는 스스로 만들지 않고 곧바로
거부한다. 순서는 반드시 `plan` → 사람이 `?` 를 채움 → `apply` 다.

> [!CAUTION]
> **이 저장소를 고쳐도 되는지 다시 확인한다.** `readOnlyRepos` 는 push 명령만 막고,
> 참고 저장소 여부는 저장소 안에 적혀 있지 않다 - `apply` 는 그것을 모른 채 파일을
> 옮긴다. §2 에서 확인받지 않았다면 여기서 사용자에게 묻는다.

병행 작업 모드 저장소(`docs_<id>/` 개인 폴더가 있는 경우)의 개인 폴더 문서는 `worker`
로 분류되어 **제자리에 남는다.** 공용 `docs/` 로 모으고 싶으면 사람이 매핑을 직접
고친다.

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/notes_adopt.py" apply --confirm <저장소 폴더 이름>
python "${CLAUDE_PLUGIN_ROOT}/scripts/notes_adopt.py" verify
```

`apply` 는 `girok-adopt-before-<날짜>` 태그를 남기고, 문서가 옮겨간 자리에 맞춰
`.claude/girok.json` 의 `board`·`decisionsDir` 을 함께 고친다. **커밋은 하나가 아니다** -
이미 git 이 있던 저장소에서는 `.gitignore` 정비 커밋이 먼저 생기고 이식 커밋이 뒤에
온다(사실상 상시 두 개다). 되돌릴 때 커밋 하나만 되돌리면 절반만 되돌아간다.
`git push` 는 태그를 함께 올리지 않으니 **`git push --tags` 로 따로 올릴 것** - 원격이
아직 없으면 `git remote add origin <주소>` 뒤 `git push -u origin <브랜치> --tags` 로
커밋과 태그를 함께 올린다.

이동 중 어디서든 막히면(이름 충돌, 자기 자신 병합 등) **그 시점에 이미 백업과 복원
태그는 만들어져 있다** - 안내가 실제 태그 이름과 백업 폴더 이름을 그대로 찍어준다.
`verify` 가 실패해도 마찬가지로 그 자리에서 복원 방법을 안내하고 멈춘다. 스스로 고치려
들지 않는다 - 무엇이 어긋났는지 모르는 채로 손대면 백업이 유일한 사실이 된다.

> [!CAUTION]
> 병합은 **이어붙이기만** 한다. 원문을 요약하거나 다시 쓰지 않는다. 다듬는 것은
> `verify` 가 통과한 다음 세션에 사람이 볼 때 할 일이다.

> [!NOTE]
> `verify` 가 증명하는 것은 정해져 있다. 링크가 재작성되지 않은 이동 문서는 바이트
> 단위(sha1)로 원본과 같은지 본다. **링크가 재작성된 문서는 바이트가 달라지는 것이
> 정상이다** - 그때는 링크 목적지를 지운 나머지 본문이 백업의 원본과 같은지 대조한다.
> 병합 문서는 원본의 모든 줄이 결과 안에 (양끝 공백을 뺀 채로) 들어있는지만 본다 - 줄
> 순서가 바뀌거나 같은 줄이 중복돼도 통과한다. 매핑에 오르지 않은 문서(마크다운이
> 아니거나 애초에 분류에서 빠진 것)는 검사 범위 밖이다.

이식 과정에서 비밀·대용량 파일이 이미 git 에 커밋돼 있으면 `.gitignore` 를 추가해도
그 파일은 이력에서 빠지지 않는다는 안내가 뜬다. **이력을 다시 쓰지 않는다** - 비밀이면
값을 폐기하고 새로 발급하는 것이 답이다.

`notesDir` 가 `"."` 인 저장소(문서가 루트에 흩어져 있는 경우)라면 **한 번 물어볼 값이
있다** - 문서를 `notes/` 아래로 모을 것인지. 이식은 기본적으로 현행 `notesDir` 를
유지한다. 바꾸면 모든 문서 경로가 달라져 링크 재작성량이 몇 배가 되고, `notesDir: "."`
는 girok 이 허용하는 정식 값이라 안 바꿔도 표준 위반이 아니다. **사람이 명시적으로
원할 때만** `.claude/girok.json` 의 `notesDir` 를 먼저 고치고 `plan` 을 다시 돌린다.

### 3. sync - 스냅샷이 낡았을 때

무엇이 바뀌는지 먼저 보여주고 진행한다.

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/method_sync.py" sync
```

sync 는 `.method/` 를 다시 쓰면서 `.claude/settings.json` 의 훅 등록도 함께 맞춘다.
**바뀌었으면 그 파일도 같이 커밋한다** - 등록이 커밋되지 않으면 다른 머신에서는 훅이
걸리지 않고, 그 상태는 정상과 겉모습이 같다. 기존 `permissions`·마켓플레이스 항목은
건드리지 않고 `hooks` 키만 갈아끼운다.

진행기록 폴더가 하위 폴더이면 sync 는 **저장소 루트에서 그 폴더까지 내려가는 폴더마다**
같은 등록을 `<폴더>/.claude/settings.json` 에 쓴다(`[등록] <폴더>/.claude/settings.json`).
Claude Code 는 세션을 시작한 폴더의 설정만 읽고 위로 올라가지 않으므로, 이 파일이 없으면
그 폴더에서 연 세션에는 훅이 걸리지 않는다. 이 파일들도 같이 커밋한다.

sync 는 `<진행기록폴더>/CLAUDE.md` 의 부트스트랩 게이트 문언도 이 판본에 맞춘다
(`<!-- girok:bootstrap:begin -->` ~ `end` 사이만). 블록 바깥은 손대지 않는다. 사람이
고쳐 써서 알아볼 수 없으면 `[확인]` 로 보고만 하고 갱신하지 않는다 - 그 경우 현재 문언은
`.method/RULES.md` 머리에 있다고 안내한다.

`.method/` 는 사람이 손대지 않는 폴더다. 사람이 고친 흔적이 있으면 `[제거]` 로 보고되며,
그 사실을 사용자에게 알린다 - 그 편집은 사라진다.

MAJOR 버전이 올랐으면 `migrations/` 에 해당 문서가 있는지 확인해 함께 안내한다.

### 4. 점검 - 정상일 때

세 가지를 실행하고 결과를 요약한다.

```
python "${CLAUDE_PLUGIN_ROOT}/scripts/method_sync.py" verify
python "${CLAUDE_PLUGIN_ROOT}/scripts/check_docs.py"
python "${CLAUDE_PLUGIN_ROOT}/scripts/marker_scan.py"
python "${CLAUDE_PLUGIN_ROOT}/scripts/notes_adopt.py" plan --dry-run
```

`--dry-run` 은 표만 출력하고 `.claude/girok-adopt.json` 을 건드리지 않는다. 점검에서
빼면 사람이 채운 `?` 해소와, 이미 이식한 저장소의 추적표가 덮어써진다.

그리고 현황을 한 문단으로 보고한다:

- 안전 게이트 OPEN 개수 (모듈이 켜져 있으면)
- 미push 커밋 (`git status -sb`)
- 상대 작업자의 새 내용 - `python "${CLAUDE_PLUGIN_ROOT}/hooks/incoming.py"` (세션 시작 때와
  같은 반입 스캔을 지금 다시 돌린다. `git fetch` 만 하고 아무것도 쓰지 않는다)
- 검사기·마커 스캔 실패 항목
- 이식 안 된 문서 (`role` 이 `?` 이거나 제자리가 아닌 항목 수) - 사람이 "제자리로 확정"
  한 문서는 매핑에서 `role: "keep"` 이라 여기 세지 않는다

## 하지 않는 것

- **게이트 항목을 닫지 않는다.** 확인자 칸은 사람이 채운다.
- **병합을 자동으로 하지 않는다.** 반입 내용이 있으면 요약을 제시하고 승인을 받는다.
- **`.method/` 를 손으로 고치지 않는다.** 개정은 플러그인 원본에서 한다.
- **force push 를 제안하지 않는다.**
- **백업 없이 파일을 옮기지 않는다.** `backup` 이 실패하면 거기서 멈춘다.
- **병합할 때 원문을 고쳐 쓰지 않는다.** 이어붙이고 출처를 남긴다.
